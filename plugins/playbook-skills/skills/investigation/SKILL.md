# Investigation

원인이 불명확한 문제를 **추측 기반 수정 반복** 대신 가설과 통제된 실험으로 좁힌다. 수정 시도가 한 번 실패했는데 그 이유를 증거로 설명할 수 없다면, 두 번째 추측 수정을 하지 말고 이 절차로 전환한다.

## 기록 위치 결정

경로를 하드코딩하지 않는다. 위에서부터 순서대로 해결한다.

1. 사용자가 이번 요청에서 지정한 경로
2. `AGENTS.md` / `CLAUDE.md` 의 문서 규약
3. `docs/README.md` 라우터
4. 저장소 탐지 — `**/investigation*`, `docs/investigations/**`, `**/debug*.md`, 기존 조사 노트. **기존 관행이 이 스킬의 기본값과 달라도 기존 관행을 따른다.**
5. 아무것도 없으면 `docs/investigations/active/<problem>.md` 를 제안하고 **한 번 묻는다.** `docs/` 트리를 통째로 만들지 말고 필요한 파일 하나만 만든다. 조사가 짧게 끝날 것 같거나 사용자가 파일을 원하지 않으면 같은 구조를 대화 안에서 유지한다.

경로가 정해지면 "이 규약을 `AGENTS.md`에 기록할까요?"를 **제안하고 승인받은 경우에만** 추가한다.

## 시작

1. 관련 코드, 로그, 테스트, 저장소 규칙을 먼저 읽는다.
2. **재현 가능한지** 판단한다. 재현이 안 되면 그것 자체가 첫 번째 조사 대상이다.
3. `Baseline`을 고정한다 — 환경, 데이터, 입력, 현재 측정값, **재현 명령**. 실험 전에 기준값이 없으면 결과를 해석할 수 없다. 문서·`AGENTS.md`가 정한 명령이 보고된 증상을 재현하지 못하면(다른 오류로 실패하는 등) 그 출력을 기록하고, 증상을 재현하는 명령을 찾아 Baseline으로 삼되 두 명령의 차이를 적는다.

코드를 곧바로 크게 수정하지 않는다.

## 실험 루프

실험마다 아래를 기록한다. 구조와 예시는 `references/investigation-structure.md`를 읽고 따른다.

```text
Observation → Hypothesis → Experiment → Expected Result → Actual Result → Interpretation → Next
```

규율:

- **한 번에 한 변수만 바꾼다.** 두 개를 동시에 바꾸면 어느 쪽이 원인인지 알 수 없다. 여기서 "변수"는 통제된 축 하나다. 커밋 범위나 설정 묶음을 절반으로 가르는 bisect도 그 축 하나만 바꾸면 허용된다. 범위가 좁혀지면 개별 변수로 다시 나눈다.
- 가설은 서로 **구분 가능**해야 한다. 같은 실험으로 둘 다 지지되면 가설을 다시 나눈다.
- 실험 **전에** 예상 결과를 쓴다. 나중에 쓰면 사후 합리화가 된다.
- 재현 명령, 입력, 환경, 로그 원문을 보존한다.
- 해석은 `Supported` / `Rejected` / `Inconclusive` 중 하나로 명시한다. `Inconclusive`를 `Supported`로 반올림하지 않는다.
- **상관관계를 원인으로 단정하지 않는다.**
- 임시 진단용 변경(로그 추가, 코드 주석 처리)은 제품 수정과 분리하고, 조사가 끝나면 되돌린다.
- 기존 사용자 변경은 보존한다.
- 다음 실험은 **정보 가치가 가장 큰 것**을 고른다. 가능하면 후보를 절반으로 가르는 실험.

아직 답하지 못한 질문은 `Open Questions`, 연결된 ADR은 `Related Decisions`에 둔다.

## 중단 조건

시작할 때 중단 조건을 정한다. 사용자가 정하지 않았다면 기본값을 밝히고 **승인을 기다리지 않고** 진행한다. 기본값: "실험 3회 안에 원인 확인 기준을 만족하지 못하면 현재까지의 증거와 남은 가설을 보고하고 멈춘다." 가설이 하나로 좁혀졌지만 확인 기준(예: 양방향 재현)을 채울 수 없는 경우도 여기에 해당한다."

중단 조건에 도달하면:

- 기록의 `Status`는 `active`로 두고 `Findings`, `Ruled Out`, `Open Questions`, 다음으로 정보 가치가 큰 실험을 채운다.
- 보고에서 중단 사실과 계속할지 여부를 묻는다.
- 다음 세션에서 이어갈 예정이면 `session-handoff` 스킬로 인계 문서를 만들고 조사 기록 경로를 링크한다.

조사가 원래 문제와 무관한 영역으로 번지면 별도 workstream으로 분리한다.

## 원인 확인 기준

다음을 **모두** 만족할 때만 "원인이 확인됐다"고 쓴다. 하나라도 빠지면 가설은 `Supported`일 뿐 확정이 아니다.

1. **양방향 재현** — 원인으로 지목한 변수를 통제하면 Baseline 재현 명령에서 문제가 사라지고, 되돌리면 다시 나타난다.
2. **같은 측정 방식** — Baseline과 같은 재현 명령·입력·환경으로 비교한다. 측정 방식을 바꿔서 얻은 개선은 증거가 아니다.
3. **간헐적 문제는 횟수로** — Baseline 실패율을 N회 반복으로 먼저 측정하고, 통제한 경우와 되돌린 경우도 같은 N회로 측정한다. N은 Baseline 실패율로 볼 때 우연히 전부 통과할 가능성이 충분히 낮게 고른다 (예: Baseline 20회 중 6회 실패 → 통제 후 20회 중 0회, 되돌린 뒤 1회 이상 실패). 가능하면 원인 변수를 고정해 결정적으로 재현하고, 문제가 **나타나는 값과 사라지는 값을 모두** 보인다 (예: 난수 시드, 타임존·로캘 같은 환경 변수, 테스트 실행 순서). 재시도처럼 증상만 가리는 조치로 사라진 것은 통제가 아니다.
4. **대안 배제** — `Hypotheses` 표에 원인 후보가 둘 이상 있었고, 남은 `Open` 가설이 같은 결과를 설명할 수 없음을 적는다.

## 종료

종료 형태는 셋 중 하나다. 어느 쪽으로 끝났는지 문서 `Status`와 보고에 명시한다.

| 종료 | 조건 | Status |
| --- | --- | --- |
| 원인 확인 | 위 원인 확인 기준을 모두 만족 | `resolved` — 원인이 확인됐다는 뜻이다. 수정 적용 여부는 `Fix and Regression Test`에 `적용됨` / `권고만`으로 적는다 |
| 중단 | 중단 조건에 도달 (좁혀졌지만 확인 기준을 채울 수 없는 경우 포함) | `active` 유지, 남은 가설과 다음 실험을 기록 |
| 포기 | 사용자가 중단을 결정했거나 문제가 더 이상 재현되지 않고 원인도 모름 | `abandoned` |

원인이 확인되면 정리한다.

- **근본 원인**과 원인 확인 기준 각 항목의 증거
- **배제된 원인**과 배제 근거
- 수정 권고 (최소 범위)
- 재발을 잡을 **회귀 테스트** — 수정 전에는 실패하고 수정 후에는 통과해야 한다
- 남은 불확실성

**수정 적용 여부:** 기본값은 원인 파악까지다. 사용자가 수정을 명시적으로 요청하지 않았다면("고쳐줘", "fix" 등) 수정 권고까지 보고하고, 적용할지 묻고 멈춘다. "원인을 모르겠어", "계속 실패해", "조사해줘"는 수정 요청이 아니다. 수정까지 요청했다면(또는 원인 보고 후 승인하면) 회귀 테스트를 먼저 추가해 실패를 확인하고, 최소 범위로 수정한 뒤 회귀 테스트와 Baseline 재현 명령을 다시 실행한다.

중요한 기술 선택이 필요해지면 `decision-record` 스킬로 승격을 **제안**하고, 승인받으면 작성한다. 현재 architecture 설명이 바뀌면 갱신 후보 위치를 제시한다. 파일 삭제·이동은 승인 없이 하지 않는다.

## 완료 조건

보고 직전에 아래 항목을 하나씩 확인한다. 채우지 못한 항목은 빼지 말고 이유와 함께 보고한다.

- [ ] 기록 경로와, 그 경로를 어떤 해석 단계로 정했는지 적었다. 대화 안에서만 기록했다면 그 이유를 적었다.
- [ ] `Problem and Target`에 측정 가능한 목표가 있다.
- [ ] `Baseline`에 그대로 실행 가능한 재현 명령과 실험 전 측정값이 있다. 간헐적 문제라면 반복 횟수와 실패율이 있다.
- [ ] 모든 실험에 `Changed variable`이 하나(bisect라면 축 하나와 범위)이고, 실험을 실행하기 전에 그 실험 항목과 `Expected Result`를 기록에 먼저 적었다.
- [ ] 모든 실험의 `Interpretation`이 `Supported` / `Rejected` / `Inconclusive` 중 하나다.
- [ ] 종료 형태(원인 확인 / 중단 / 포기)를 명시했고, 원인 확인이라면 원인 확인 기준 네 항목의 증거가 있다.
- [ ] 수정을 적용했다면 회귀 테스트가 수정 전 실패·수정 후 통과했고, Baseline 재현 명령으로 `Problem and Target`의 목표 달성을 확인했다.
- [ ] `Status`가 종료 형태와 맞고, `resolved`라면 `Fix and Regression Test`에 `적용됨` / `권고만`이 적혀 있다.
- [ ] 임시 진단용 변경(로그, 주석 처리, 디버그 플래그, 진단용 파일)이 `git status`와 `git diff`에 남아 있지 않다.
- [ ] 작업 시작 전 사용자의 기존 변경이 그대로 남아 있다.
